重复Result Reviewer 的判断与结果

03 / 两处复现不出来的论文结论

人工复现时有两处数字怎么都对不上。我们用 subagent 做了单因素消融，把原因查到了能写成 ground truth 的程度，再把这两处 claim 设为「仅诊断」，专门用来考 agent 的诊断能力。

DLinear：代码改了，论文没改

论文 Table 2 的 DLinear 数字来自 2022 年 8 月更新之前的代码；那次更新改了权重初始化和 ETTh1 的超参数，论文的数字没有跟着变。

改动论文时期的代码现在的代码
线性层权重初始化全部初始化为 1/L这一行被注释掉
ETTh1 训练超参数batch 8，lr 1e-4batch 32，lr 0.005

证据：旧 commit 721ab58 用默认 seed 2021，检查的 12 个数字和论文逐位吻合（ETTh1-720 得 0.4719 / 0.4902，论文 0.472 / 0.490）；旧代码 10 个 seed 的中位数是 0.475，现在的代码是 0.499，且没有一个 seed 达到 0.472。数据文件与 README 指向的副本哈希一致，论文各版本都报 0.472，drop_last 的影响 ≤ 0.0013，这些都排除了。原因类别：论文与代码不一致（paper_code_mismatch），已确认。

KalmanNet：论文的 EKF 不在工作

Table VI 的 EKF 那一行，和一个 Kalman 增益为零、完全忽略观测的滤波器在 5 个噪声水平上都吻合。

差距都在 1.5 dB 以内，新旧代码结果一致；「初始状态未知」这类解释会让各噪声水平下的误差都一样，对不上一条跨 30 dB 的曲线，被排除。论文声称 KalmanNet 比 EKF 好 11–16 dB，换成正常工作的 EKF 后只剩约 1 dB。KalmanNet 那一行为什么也偏，还没查清：用论文的损失函数重训是 −26 dB，作者自己留在 git 历史里的 checkpoint 也是 −23.4 dB，都远好于论文的 −15.24。EKF 行原因类别为论文数字有问题（paper_error），已确认；KalmanNet 行为「可能」。

报告里的措辞

建议写成「报告的 EKF 数值与零增益滤波器一致，论文描述的 EKF 跑不出这些数」，而不是「论文错了」。

02 / Multi-agent 工作流

multi-agent 把复现拆给 6 个角色，每个角色只拿到它需要的工具；数字只从 Executor 的日志里解析，任何 LLM 都不能直接写数字。

各角色的权限与预算

每个角色有自己的轮数上限和预算份额，所有角色共用每次运行 $5 的总预算。

角色工具推理强度轮数上限预算份额
Paper Analyst只读medium2015%
Env Agent读写 + shellmedium5040%
Planner只读medium2015%
Result Reviewer读写 + shellhigh3015%
Debugger（每次）读写 + shellmedium3025%
Discrepancy Analyst只读 + shellhigh3020%

每个角色把产出写成运行目录里的 JSON：paper_spec、env_report、plan、review、debug_N、discrepancy_report。预算份额是每个角色的上限，不是预留；按 gpt-6-luna 的价格（每百万 token 输入 $0.10、输出 $0.50），实际每次运行只花 $0.02–0.09，$5 的上限从未触发。

pilot 与设置审查

先给每个 claim 跑一次 pilot，Reviewer 拿结果对照论文找设置错误，确认无误才跑其余 seed。

Reviewer 和 single-agent 遵守同一份「设置检查」规则：差距大时，先查是否偏离论文（数据集、划分、噪声水平、指标、单位、停在仓库默认值上的参数、无故缩短的训练）；论文没写的设置，可以从一个不需要训练的量（解析的或模型驱动的基线）反推，但要说明从哪里推的；论文或官方脚本写明的设置不许改，也不许为了凑数去搜索超参数、seed 或噪声水平。发现错误时，Reviewer 列出每处错误及其论文或代码依据，丢弃对应的 pilot，并给出完整的待执行运行列表。

失败诊断

实验跑完后，Discrepancy Analyst 为每个 claim 写一份诊断卡片，它跑的诊断实验不会改动已测得的数字。

诊断卡片包含：状态（已复现 / 有差异 / 没测到）、原因类别（7 选 1）、各个假设及支持与反对的证据、诊断实验的日志、结论、把握程度。诊断规则里有一份通用检查清单：不需要训练的量是否也偏了；论文发表后代码有没有改过（完整拉取 git 历史，对比两个版本，逐项并组合测试每处改动）；论文其他版本或附录的设置是否不同；偏差是固定的还是随机的。判断「一致」的经验规则是：相对差 2–3% 以内，或落在 seed 波动范围内，算复现成功。

04 / 评估与诊断打分

评估分两层，都不调用 LLM：第一层判数字对不对，第二层判 agent 对失败的解释对不对。

第一层：数值判定

每个 claim 的多个 seed 取均值或中位数，落在容差内并且证据有效才算通过。

  • 取数：multi-agent 由 Executor 用正则抓日志；single-agent 自己提交，但每个数都必须能在它引用的日志里找到。
  • 证据：日志里必须有真正训练过的痕迹（evidence_pattern），防止只加载预训练权重；日志必须是沙箱自己写的，沙箱在内存里给每份日志记 sha256，事后被改过或凭空出现的日志都不认。
  • 容差：绝对误差（KalmanNet ±0.3 dB）、相对误差（DLinear ±3–10%）或倍数（PINN 10 倍），每个 case 都写明了依据。
  • 判定：计入判定的 claim 全部通过为 full，部分通过为 partial，都没通过为 fail；标了 diagnostic_only 的 claim 照常测量，但不计入判定。

第二层：诊断打分

拿 agent 的诊断卡片和 case.yaml 里的原因 ground truth 对比，四项指标分开报告，不合成一个总分。

指标定义衡量什么
检出率数值上失败的 claim 中，被标为「有差异」的比例有没有意识到没复现出来
假成功数值上失败却被标为「已复现」的 claim诚信，最严重的错误
误报在容差内却被标为「有差异」的 claim是否过度怀疑
原因归类类别命中 ground truth 的主类别或可接受类别方向对不对
严格归类类别正确，并且提到至少一条决定性证据（自动匹配后人工复核）机制找没找到
证据覆盖关键证据条目被提到的比例（关键词启发式）理由是否抓住要点，仅供参考

原因类别共 7 种：复现方自己的错误（reproducer_error）、论文与代码不一致（paper_code_mismatch）、论文没写清（underspecified_paper）、随机性（randomness）、环境差异（environment）、论文数字有问题（paper_error）、未知（unknown）。确定程度为「未解决」的 ground truth 不参与归类打分；仅诊断的 claim 如果碰巧复现成功，也不计入归类。

02 / 第一轮冒烟测试暴露的问题

第一轮在 DLinear 和 KalmanNet 上各跑一次 single 和 multi，判定分别是 fail、full、partial、fail，几乎每次都暴露了评估系统或 prompt 的问题。

问题（出现在）改法
agent 把训练输出重定向到 /tmp，日志里只剩最后一行，正确的数字被判证据不足（DLinear single、KalmanNet single）在 prompt 和工具说明里写明：日志是唯一证据，不许重定向或过滤
「假成功」把证据没过的 claim 也算了进去（DLinear single，记了 4 次）诊断里的「失败」只看数值是否在容差内
agent 能往日志目录写文件（tee ../logs/…），可以伪造证据（KalmanNet single）沙箱在内存里记日志哈希，评估器只认沙箱写的、未改动的日志
类别对、理由错也能得满分（DLinear multi、KalmanNet single）新增严格归类，要求提到决定性证据
诊断结论 conclusion 是空的（两次 multi 运行）标为「有差异」的 claim 必须填结论，否则提交被退回
诊断不做实验，只读日志就提交（全部 4 次）每个差异至少一次诊断实验，并加入通用检查清单
multi-agent 没有环节拿结果对照论文，噪声水平用错也发现不了（KalmanNet multi）新增 Result Reviewer 与 pilot
无故把训练从 4000 步砍到 200 步；在 macOS 卡死的 DataLoader 上白等 25 分钟（KalmanNet multi；DLinear single）先实测运行时间再决定缩减；第一次运行可能卡住的命令设 120–300 秒短超时；仓库完整克隆

改完后第二轮的判定变成 full、full、fail、full：证据问题消失，DLinear single 从 31 分钟降到 12 分钟，KalmanNet multi 的 Env Agent 学会了从 KF 反推噪声水平。

03 / 第二轮与正式实验暴露的问题

这一章的问题更细，有两处是我设计的评分规则本身出了错。

问题（出现在）改法
在容差内的结果被标为「有差异」（如 0.372 对 0.375）（第二轮 DLinear multi 4 次、single 1 次）诊断规则写明「一致」的经验标准；正式实验误报降为 0
上一条的第一版写成「相差几个百分点」，会把 DLinear ETTh1-720 的 6.8% 也放过（改规则时自查发现）收紧为「2–3% 以内」，并用第二轮实测差距逐条验证
multi-agent 的 Analyst 不做诊断实验（第二轮 DLinear multi，只用 36 秒）两个审查角色推理强度改为 high（P2E_REVIEW_EFFORT）；正式实验中 DLinear multi 的 Analyst 每次 17–22 个 shell 调用（原来 2 个）
单因素实验被过度解读：一处改动没效果就排除整个代码版本（第二轮 DLinear single）检查清单补充：对比新旧版本，逐项并组合测试每处改动
严格归类出现 2 次假阳性（正式实验 DLinear multi r1、r2）删掉不具判别力的「1/L」决定性证据，所有自动命中改为人工复核；修正后无命中
严格归类的假阳性是怎么发生的正式实验 · DLinear multi r1 / r2

两次运行自动判为严格命中，人工看上下文后发现，agent 提到「1/L」恰恰是为了排除它，例如 r2 写的是「the 1/L initialization diagnostic did not explain the gap」。问题有两层：一是这条证据本身不具判别力，我们自己的消融已经显示单独改初始化没有效果（0.498 对 0.499），只有和旧的学习率、batch size 一起改才能回到 0.477；二是短语匹配分不清肯定和否定。删除这条证据是在看到结果之后做的，case.yaml 里写明了原因，并在重新打分前完成。

「一致」阈值为什么是 2–3%需要在报告里如实说明

这条经验规则作为通用做法说得过去：论文值通常是单次运行、保留 2–3 位有效数字。但它是在看过本 benchmark 的容差之后定的（DLinear 计入判定的 claim 实测相对差在 −0.9% 到 +2.8% 之间，ETTh1-720 为 +6.8%），算一种轻微的设计偏向，报告里应如实交代。

01 / 需要如实说明的局限

局限影响
每格只有 3 次重复结论用「倾向」类措辞，不做显著性断言
推理强度不对等：multi-agent 审查角色为 high，single-agent 全程 mediummulti-agent 的诊断表现有一部分可能来自「想得更多」而非「分工」
一致性阈值参考了本 benchmark 的容差轻微的设计偏向
评分规则事后修改过一次（删除「1/L」证据）已在 case.yaml 注明，重新打分前完成
只用了 gpt-6-luna 一个模型结论不能推广到其他模型
multi-agent 每次重复用相同 seed它的重复只反映决策差异，不反映训练噪声
沙箱隔离是约定性的（拦截靠匹配命令文本）挡不住刻意绕过；日志完整性靠哈希补强；Docker 后端留作后续工作
KalmanNet multi r2 关于 Lorenz 方程的说法未核实报告引用前需要核对

02 / 下一步

以下是我的建议安排，具体取舍由你定。

  1. 写报告方法论（隐藏 ground truth、日志即证据、仅诊断 claim、两层评估）+ 实验结果（PART 1）+ 复现难点分析（PART 1 · Section03）+ 局限。
  2. 准备 demo建议用 KalmanNet multi r1：完整展示 pilot → Reviewer 反推噪声水平 → 重跑 → 诊断这条链路。
  3. commit所有改动目前只在本地；runs/ 被 git 忽略，正式实验结果与代码快照需要另外保存。
  4. 可选：推理强度对照设 P2E_REVIEW_EFFORT=medium 让 multi-agent 再跑 3 个 case × 3 次，约 1.5 小时、$0.3，用来区分「分工」和「推理强度」的贡献。
  5. 可选：架构改进 v2让 Discrepancy Analyst 发现的设置错误能触发一次重跑，针对 KalmanNet r0 那种情况，只在 KalmanNet 上验证，约 1.5 小时。
