01 / 项目现状

Paper2Experiment 让 LLM agent 复现工程类论文：给它论文 PDF 和官方仓库，它在沙箱里搭环境、跑实验、提交数字；一个不用 LLM 的评估器拿隐藏的 ground truth 打分，并给 agent 对失败的解释打分。项目对比三种做法：不用 LLM 的 deterministic baseline、一个 agent 包办的 single-agent、多个角色分工的 multi-agent。

和 10/4 那期相比，benchmark 新增了 SGC 和 FITS 两篇论文（人工复现都是 full）；系统在新论文上暴露出 4 个设计缺陷，修复后定为 v2 版本，并按 5 个 case × 2 种 workflow × 3 次重复重跑了正式实验，共 30 次，用时 7.0 小时，花费 $1.03。系统现在冻结在 v2。

诊断：方向对，机制难

最深的一次诊断翻了 git 历史、隔离出一个因素，但 10 个 seed 的复核否定了它给出的机制。

v2 的 DLinear multi r2 发现旧代码里有一个 forward 从不使用的 Linear_Decoder 层：它的初始化会消耗随机数，从而改变固定 seed 下的 minibatch 顺序；只加回这一层，3 个 seed 的中位数降到 0.4805，回到容差内。严格归类因此自动命中。用 10 个 seed 复核：

ETTh1-720，各 10 个 seed中位数范围容差内3 个 seed 中位数达标的概率
现行代码0.4990.478–0.6153/1018%
现行代码 + 未使用的 decoder0.4820.475–0.5256/1067%
论文时期的完整旧代码0.4750.471–0.48410/10100%

agent 的观察能复现（seed 2021 正好 0.4804），10 个 seed 的中位数也确实降了（单侧置换检验 p = 0.028）。但一个不参与计算的层只是把每个 seed 映射到另一串随机数，在所有 seed 上的结果分布不变，所以这更可能是重尾、高方差设置下的抽样波动；能稳定复现论文的只有完整的旧代码（更小的学习率和 batch）。人工判定：方向对（代码版本），机制不成立，算半个。

3 个 seed 的诊断实验可能制造假机制

当 seed 之间的波动和要解释的差距一样大时，一个单因素实验配 3 个 seed，足以得到看上去很有说服力的「机制」。这一条值得作为方法论教训写进报告，也说明严格归类必须人工复核。

03 / 论文本身的问题

人工复现和系统运行在四篇论文里发现了论文与代码、论文与自身的不一致。前两处复现不出来，设为「仅诊断」claim，专门考 agent 的诊断能力；后两处能复现，但暴露了陷阱或协议问题。

DLinear：代码改了，论文没改

Table 2 的 DLinear 数字来自 2022 年 8 月更新之前的代码；那次更新改了权重初始化和 ETTh1 的超参数，论文的数字没有跟着变。

旧 commit 721ab58 用默认 seed 2021，检查的 12 个数字和论文逐位吻合（ETTh1-720 得 0.4719 / 0.4902，论文 0.472 / 0.490）；旧代码 10 个 seed 的中位数 0.475，现行代码 0.499。那次更新还删掉了未使用的 decoder 层，它只影响随机数流，不是原因（PART 1 · Section02）。原因类别：论文与代码不一致，已确认。

KalmanNet：论文的 EKF 不在工作

Table VI 的 EKF 那一行，和一个 Kalman 增益为零、完全忽略观测的滤波器在 5 个噪声水平上都吻合（误差 1.5 dB 以内）。

1/r²−100102030 dB
论文的 EKF26.3821.7814.504.84−4.02
零增益 EKF（我们跑的）27.322.714.54.5−5.5

论文声称 KalmanNet 比 EKF 好 11–16 dB，换成正常工作的 EKF 后只剩约 1 dB；KalmanNet 那一行为什么也偏还没查清。报告措辞建议写成「报告的 EKF 数值与零增益滤波器一致」，而不是「论文错了」。

SGC：正文和 README 不一致

论文正文写训练 100 个 epoch，README 给 Citeseer 的命令是 150 个；只有 150 个能复现表格（71.84 对 71.9），100 个得 71.2。

README 附带的 weight decay 接近在 150 个 epoch 下调出的值，作者很可能就是按 150 调的参（推测）。按你选的方案 (a)，系统现在用官方命令测量，并把正文的设置跑一次作诊断。

FITS：在测试集上选参数

论文说超参数按验证集选，但官方日志里每个 _best 配置都是测试集上最好的那个；真按验证集选，ETTh2-96 会差 5.4%。

数字本身能复现（四项都在 0.15% 以内，CPU 结果与作者的 GPU 日志逐个 seed 吻合到 1e-6），所以这不影响判定；它暴露的是系统的范围限制：系统只检查「数字能不能复现」，不检查「官方配置是否符合论文描述的流程」。两种 workflow 都没有发现这一点。

02 / Multi-agent 工作流

multi-agent 把复现拆给 6 个角色，每个角色只拿到它需要的工具；数字只从 Executor 的日志里解析，任何 LLM 都不能直接写数字。

各角色的权限与预算

每个角色有自己的轮数上限和预算份额，所有角色共用每次运行 $5 的总预算。

角色工具推理强度轮数上限预算份额

预算份额是每个角色的上限，不是预留；按 gpt-6-luna 的价格，v2 每次运行只花 $0.007–0.09，$5 的上限从未触发。

设置检查规则

Reviewer 和 single-agent 遵守同一份规则：先查是否偏离论文，再决定要不要修正，修正必须有论文或代码依据。

  • 常见设置错误：数据集、划分、噪声水平、指标、单位、停在仓库默认值上的参数、无故缩短的训练。
  • 论文没写的设置：可以从一个不需要训练的量（解析的或模型驱动的基线）反推，但要说明从哪里推的。
  • 正文与官方命令冲突（v2 新增）：测量用作者给的复现命令或脚本，正文的设置跑一次作诊断，两者都报告；只是代码默认值、没有复现命令设置过它的，仍以论文为准。
  • 禁止：修改论文或官方脚本写明的设置；为了凑数搜索超参数、seed 或噪声水平。

失败诊断

实验跑完后，Discrepancy Analyst 为每个 claim 写一份诊断卡片，它跑的诊断实验不会改动已测得的数字。

诊断卡片包含：状态（已复现 / 有差异 / 没测到，v2 起按预注册标准判断）、原因类别（7 选 1）、各个假设及支持与反对的证据、诊断实验的日志、结论、把握程度。检查清单要求：看不需要训练的量是否也偏了；论文发表后代码有没有改过（完整拉取 git 历史，对比两个版本，逐项并组合测试每处改动）；论文其他版本或附录的设置是否不同；偏差是固定的还是随机的。

04 / 评估与诊断打分

评估分两层，都不调用 LLM：第一层判数字对不对，第二层判 agent 对失败的解释对不对。

第一层：数值判定

每个 claim 的多个 seed 取均值或中位数，落在预注册的容差内并且证据有效才算通过。

  • 取数：multi-agent 由 Executor 用正则抓日志；single-agent 自己提交，每个 seed 一个值，不能交均值。
  • 证据（v2）：每个值必须出现在一份同时匹配证据模式的日志里；证据模式只匹配训练过程的痕迹，不绑定输出格式；手动打印的数字不能单独作证据；每个 claim 都有证据模式。
  • 完整性：日志必须是沙箱自己写的，沙箱在内存里给每份日志记 sha256，事后被改过或凭空出现的日志都不认。
  • 判定：计入判定的 claim 全部通过为 full，部分通过为 partial，都没通过为 fail；仅诊断的 claim 照常测量，但不计入判定。

第二层：诊断打分

拿 agent 的诊断卡片和 case.yaml 里的原因 ground truth 对比，各项指标分开报告。

指标定义衡量什么
检出率数值上失败（没有值或聚合值超出容差）的 claim 中，被标为「有差异」的比例有没有意识到没复现出来
假成功数值上失败却被标为「已复现」的 claim诚信，最严重的错误
误报在容差内却被标为「有差异」的 claim是否过度怀疑
原因归类类别命中 ground truth 的主类别或可接受类别方向对不对
严格归类类别正确，并且提到决定性证据（自动匹配后人工复核）机制找没找到
证据覆盖关键证据条目被提到的比例（关键词启发式）仅供参考

seed 数不够或证据不足只影响第一层的判定，不计入诊断里的「失败」，否则数字正确的 claim 会被算成假成功（v2 修正）。

两次运行自动判为严格命中，人工看上下文后发现，agent 提到「1/L」恰恰是为了排除它。问题有两层：这条证据本身不具判别力（单独改初始化没有效果，0.498 对 0.499）；短语匹配分不清肯定和否定。删除这条证据是在看到结果之后做的，case.yaml 里写明了原因，并在重新打分前完成。

04 / 新 case 与 v2 暴露的问题

用两篇新论文对比人工复现和系统运行时，SGC 上两边结论不一致（人工 full，系统 single fail、multi partial），顺着查出了下面的缺陷；v2 正式实验又发现了一处。

问题（出现在）改法
全局的「2–3% 算一致」规则让两种 workflow 都把 Citeseer 差 0.7 pp 判成「已复现」，而容差是 0.5 pp（SGC，我上一轮引入的）删除全局阈值，改为预注册：runner 把每个 claim 的容差写进任务说明，agent 和评估器用同一个标准
正文与官方命令冲突时没有规则，两种 workflow 都选了正文的 100 个 epoch（SGC）方案 (a)：测量用官方命令，正文设置跑一次作诊断，两者都报告
single 把 3 个 seed 的均值当成一个值提交，n = 1 被判失败（SGC）schema 写明每个 seed 一个值；少于 seed 数的提交被退回
agent 用 Python 打印手写的数字，「数字出现在日志里」的检查居然通过（SGC）每个值必须出现在匹配证据模式的日志里；给 9 个缺证据模式的 claim 补上；GCN 补跑人工复现日志
seed 不够也被算成假成功（SGC）诊断只统计数值偏差
证据模式绑定了最后一行的输出格式，合法修改输出的运行被误判（v2 FITS single r1）证据模式只匹配训练痕迹，所有运行统一重新打分

修复后 SGC 重跑，两种 workflow 都从 fail / partial 变成 full，Citeseer 71.83，并按冲突规则把 100 个 epoch 的诊断结果（71.2）写进了报告。

修一处可能坏另一处

「2–3%」规则在 DLinear 上消除了误报，到 SGC 上却制造了假成功；证据规则堵上了手写数字的漏洞，又误伤了合法修改输出格式的运行。只有 3 个 case 时看不出这种「对 benchmark 过拟合」，加了新 case 才暴露。根本解法是把判定标准写明（预注册），而不是继续调阈值。

01 / 需要如实说明的局限

局限影响
每格只有 3 次重复结论用「倾向」类措辞，不做显著性断言
推理强度不对等：multi-agent 审查角色为 high，single-agent 全程 mediummulti-agent 的诊断表现有一部分可能来自「想得更多」
评分规则事后修改过两次（删除「1/L」证据；证据模式改为只匹配训练痕迹）都在 case.yaml 注明原因，并对全部 48 次运行统一重新打分
预注册的容差是在人工复现之后定的容差反映人工复现观察到的波动，不是事先的独立设定
KalmanNet 的噪声水平推断只有约 58% 的运行做到规则只写了「可以推断」；改成「应当」属于针对单个 case 调 prompt，留作后续工作
系统只检查数字能不能复现，不检查协议是否符合论文描述FITS 在测试集上选参这类问题发现不了
只用了 gpt-6-luna 一个模型；multi-agent 每次重复用相同 seed结论不能推广到其他模型；multi 的重复只反映决策差异
沙箱隔离是约定性的挡不住刻意绕过；日志完整性靠哈希补强；Docker 后端留作后续工作

02 / 下一步

以下是我的建议安排，具体取舍由你定。系统已经冻结在 v2。

  1. commit冻结 v2 时提交一次；正式实验结果与代码快照在 runs/ 下，需要另外保存。
  2. 写报告方法论（隐藏 ground truth、预注册标准、日志即证据、仅诊断 claim、两层评估）+ v1 / v2 结果 + 论文本身的问题（PART 1 · Section03）+ 迭代过程中的教训（PART 3）+ 局限。
  3. 准备 demo候选一：v1 KalmanNet multi r1，完整展示 pilot → Reviewer 反推噪声 → 重跑 → 诊断；候选二：v2 DLinear multi r2，展示翻 git 历史、隔离因素的深度诊断，并引出「3 个 seed 不够」的教训。
  4. 可选：推理强度对照P2E_REVIEW_EFFORT=medium 让 multi-agent 再跑一遍，区分「分工」和「推理强度」的贡献。
  5. 可选：KalmanNet 推断规则把「可以推断」改成「应当推断」，只重跑 KalmanNet（约 2.5 小时、$0.4）；不建议放进主结果。
