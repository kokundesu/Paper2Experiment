01 / 结论

Paper2Experiment 对比两种 LLM workflow：single-agent 是一个拿着全部工具的 agent 包办整个复现；multi-agent 把复现拆给 6 个角色（Paper Analyst、Env Agent、Planner、Result Reviewer、Debugger、Discrepancy Analyst），数字只从 Executor 的日志里解析。这份报告把到 10 月 5 日为止的全部 64 次系统运行按代码版本分组，比较两者在复现、花费和诊断上的表现。

四句话
  • 复现：没有稳定的赢家。所有版本合计 single 26/32 判 full，multi 27/32；差距几乎全部来自 KalmanNet，而且方向随版本反转。
  • 花费：multi 在每个版本都更慢、更贵，约为 single 的 1.4 倍，请求数和工具调用约 1.6–1.7 倍。
  • 诊断：两者一样诚实（V2 假成功、误报都为 0）；multi 更深入，但原因归类的准确率因 case 而异，两者都找不到真正的机制。
  • 架构：multi 的优势（独立 smoke test、用时稳定、诊断深）和弱点（Reviewer 只判一次、诊断结果不能触发重跑）都是结构性的。

02 / 各版本一览

64 次运行按当时的代码状态分成 5 个版本。所有运行都用当前的评估器和 case.yaml 重新打分，规则一致；但各版本里 agent 看到的 prompt 和规则不同，所以跨版本的变化既有系统改进，也有随机波动。

版本划分

V0 到 V0.2 是冒烟测试，每个 case 只有一次；V1 和 V2 是正式实验，每格 3 次重复。

01 / 差距从哪里来

按 case 拆开后，五个 case 里有四个两种 workflow 的结果完全一样；唯一拉开差距的是 KalmanNet。

GCN、DLinear、FITS 两者始终一样；SGC 两者在 V1 一起掉进同一个陷阱、在 V2 一起走出来。

所以「V1 single 领先、V2 multi 领先」这个表面排名，主要是这一步判断的抽样波动，不是架构差异。两者失败的方式不同：single 偏保守，按论文用 ν = 0 dB，但噪声绝对大小留在仓库默认值，如实报告差异却不修正；multi 的 Result Reviewer 只有一次判断机会，既出现过过于保守（直接把差异交给诊断），也出现过过度修正（V1 r2 按论文正文改了观测矩阵，而正文和论文自己的表格矛盾）。

信息只能往下游流

V1 KalmanNet multi r0 里，Discrepancy Analyst 准确诊断出「噪声取 0.01 能精确复现论文」，但诊断不能回头改测量，这次运行仍然是 fail。single-agent 在同一个上下文里能反复试错，没有这个问题。这是 multi 架构最明确的改进方向：让诊断发现的设置错误能触发一次重跑。

02 / 花费与效率

花费是两种 workflow 之间唯一在每个版本都稳定的差别。

指标（V2）SingleMulti倍数
平均用时11.1 分钟15.4 分钟1.4×
平均花费$0.027$0.0391.4×
平均 LLM 请求数29461.6×
平均工具调用44761.7×

从 V1 起，multi 每个版本都贵 1.3–1.4 倍，请求数多 1.5–1.7 倍。原因是结构性的：6 个角色各自重新读论文和代码，再加上 pilot 审查和诊断两个阶段。唯一的例外是 V0.1，single 在 macOS 卡死的命令上白等了两次，反而更慢（22.5 对 8.2 分钟）；加入短超时规则后不再出现。

multi 在用时稳定性上有优势：V1 的 DLinear 上 single 的用时波动很大（±8.2 分钟），multi 只有 ±0.9 分钟。multi 的 Env Agent 会先做 smoke test 并实测运行时间，Executor 的运行一次就能跑通。

两者都能如实发现复现失败；深度上 multi 更强，但更深不等于更准。

两边各漏检的 1 个就是 V1 SGC 的那次假成功。V1 的两次假成功是同一个原因：「2–3% 算一致」这条全局规则把 SGC Citeseer 差 0.7 pp（容差 0.5 pp）判成了一致，V2 改为预注册标准后清零。V0.1 的 multi 诊断报告结论为空、全部无效，检出记 0，属于当时的 schema 问题，V0.2 已修复。

multi 更深

multi 的 Discrepancy Analyst 以 high 推理强度运行，每次 17–22 个 shell 调用，会翻 git 历史、做单因素实验。

最深的一次是 V2 DLinear multi r2：它找到 2022 年 8 月的代码更新，隔离出旧代码里一个从不参与计算的 decoder 层，3 个 seed 下结果回到容差内。10 个 seed 复核后，这个层只改变随机数流，不改变结果分布，所以判为方向对、机制错（0.5）。single 的诊断多停在表面：例如 V1 DLinear single r1 分别测了两个改动，单独都没效果，就排除了整个代码版本，而两者合起来才能回到论文的数值。

但不一定更准

在 KalmanNet 上，single 的原因归类反而一直更准。

KalmanNet Table VI 的 ground truth 是「论文数字有问题」，同样接受「论文与代码不一致」。single 6 次都选了后者；multi 多次选「论文没写清」，不在可接受范围内。两者都没想到「论文的 EKF 等价于零增益滤波器」这个真正的机制。

benchmark 区分度有限5 个 case 里只有 KalmanNet 能拉开两者，其余四个两者都能稳定成功

02 / 总体判断

  1. 复现在这个 benchmark 上，multi-agent 没有表现出稳定的优势（26/32 对 27/32）；仅有的差距来自一个 case 的一步判断，方向随版本反转。
  2. 花费multi-agent 稳定地贵约 1.4 倍，请求数和工具调用多 1.6–1.7 倍。
  3. 诊断两者一样诚实；multi 更深入，但原因归类的准确率因 case 而异（DLinear 更好，KalmanNet 更差），都找不到真正的机制。
  4. 架构multi 的优势（独立 smoke test、用时稳定、分析员深入）和弱点（一次性判断、信息不能回流）都是结构性的；后者是最明确的改进方向。
报告里建议的表述

「在本 benchmark 上，multi-agent 的价值体现在诊断深度和运行稳定性，而不是复现成功率，代价约为 1.4 倍的花费；真正的区分集中在需要判断的设置推断上，两种架构的成功率都在一半左右。」

如果要让结论更有说服力
  • 等强度对照：设 P2E_REVIEW_EFFORT=medium，multi 再跑 5 个 case × 3 次（约 4 小时、$0.6），区分「分工」和「推理强度」的贡献。
  • 信息回流：让 Discrepancy Analyst 发现的设置错误能触发一次重跑，只在 KalmanNet 上验证。
