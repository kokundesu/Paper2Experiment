## 失败的运行

90 次运行中有 7 次没有全对，涉及 5 道题：

| 题 | 工作流 | 原因 |
|---|---|---|
| 3821950 | A、B、D | 三个都失败。这是一个 R Markdown 题，环境装不起来（B 报告 `rmarkdown::render` 在 setup chunk 就停了），A 和 D 都没交出答案。问题在题目的环境本身 |
| 0152700 | B | 看图题答对了，但这次运行没有用 `view_image` 看过自己生成的图，文本里也找不到这个答案，所以无法证明答案是本次运行产出的，按我们的规则判为 partial |
| 3418007 | D | **这是评测框架的 bug，不是模型的错。** 规划器想替换一个它只在文字里描述过、从没真正加进计划的任务（`setup_env`）。补丁检查本应把这个错误退回给规划器，实际却抛出了 `KeyError`，整次运行只进行了 28 秒就中止了。已修复，并补了回归测试 |
| 4933686 | D | 从图上读 HR 读错了，读成 2.27，正确值是 2.15 |
| 9477017 | D | 列表题答错 |

如果不算那次 bug，D 是 26/29。即使重跑后答对，D 最多也只是 27/30，结论不变。

## HAL 规则为什么比我们的数字低

两套规则的差别主要来自三道题，三个工作流在这三道题上都是"我们判对、HAL 判错"：

| 题 | 原因 |
|---|---|
| 9240688 | 标准答案是 0.44，agent 答 0.438。我们的规则接受这种没经过四舍五入的答案（与 v1.1 的修正一致），HAL 不接受 |
| 2345790、3762736 | 三次人工重跑给出的数值完全一样，标准差为 0，于是 HAL 的预测区间宽度也是 0。三个相同的数取平均时会产生浮点误差，例如 99.41 算出来是 99.41000000000001，agent 答的 99.41 因此落在区间之外。这是 HAL 规则本身的数值问题 |

0152700 的 A 和 D 在 HAL 下判错，也是同样的浮点问题：p 值 2.34e-10 只在最后几位有差别。

## 和开发集的对比

| | 开发集第三轮（Haiku，v5） | 测试集 |
|---|---|---|
| 题数 | 42 | 30 |
| 平均每题问题数 | 2.3（97/42） | 1.5（46/30） |
| A | 32（76%） | 29（97%） |
| B | 33（79%） | 28（93%） |
| D | 35（83%） | 26（87%） |

- 测试集的通过率比开发集高 4 到 21 个百分点，主要是因为测试集的题更简单：每道题要回答的问题更少，30 道题里有 27 道三个工作流全都做对了。这不说明 agent 在测试集上发挥得更好。
- 工作流的排名反过来了：开发集上 D 最好，测试集上 D 最差。两边的差距都不显著，说明这个规模的样本分不出三个工作流的高下。顺带一提，开发集和测试集加起来，三个工作流都是 61/72。但开发集是用来调试 skill 和工作流的，严格来说不应该和测试集合并计算，这里只作参考。

## 写进报告时需要交代的几点

1. 测试集只跑了一次，开跑前 skill 库已经冻结，开发时试跑过的 5 道题已排除。
2. 我们的规则比 HAL 更严：除了答对，还要能证明答案是本次运行产出的。同时，我们接受没经过四舍五入的答案，HAL 不接受。两套数字都报告。
3. D 的一次失败来自评测框架的 bug。报告里应该注明，或者用修好的代码单独重跑这一次，并说明是重跑的。
4. 样本小，每组 30 道题，置信区间宽 15 到 25 个百分点。不要据此给三个工作流排名。
