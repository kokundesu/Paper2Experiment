# Paper2Experiment v4：Planner + Runtime 调度方案

方案确认于 2026-10-16，设计依据见 [reading-notes.md](reading-notes.md)。本文先讲为什么改，再讲架构和机制，最后是实验设计和实现状态。

## 1. 为什么要改

v3.0 在 5 篇新论文上的测试结果：full 15/30（single 7/15，fixed pipeline 8/15），假成功 0 次。15 次失败：

| 失败类型 | 次数 | 暴露出的问题 |
|---|---|---|
| 只是证据不合规（数字在容差内） | 6 | 验证只发生在最后；agent 过滤输出、漏掉 `--verbose`、把指标放到训练之外单独算 |
| 数字没对上 | 7 | Deep SVDD 的系统性差距，加上 HNN 1 次 |
| 数字和证据都有问题 | 1 | 同上两类 |
| 系统 bug | 1 | 目录不存在导致流程崩溃，v3.1 已修 |

两个根本原因：single 是 ReAct 式的 harness，运行中没有验证；fixed pipeline 的路由写死在代码里，上游出错，下游没有人有职责、也没有机会回头发现。

## 2. 已经确定的决定

- 继续用 **LangGraph**，按 DeepSeek Harness / Cuti 的设计原则实现，不改用 dsh。
- **不做"增量唤醒对全量唤醒"的对照实验**：它和短剧项目论文的 idea 5 重叠；这里只把增量唤醒当作工程选择。
- 开发在 `Paper2Exp` 仓库进行，每个版本一个文件夹，共享代码放在 `Base/`。
- 写完代码只跑离线测试；对比实验等用户建好论文数据集后再跑。

## 3. 架构

```
        ┌──────────── Planner（唯一的规划者，LLM）────────────┐
        │ task ledger：已确认的事实、待查、待推导、假设、计划  │
        │ 输出：ExperimentPatch（增、删、替换任务；收尾提议）  │
        └───────▲────────────────────────────────┬────────────┘
 唤醒时只给增量  │ 变了哪些任务、失败详情、错误签名、    │ patch
                │ 进度和停滞计数                         │
        ┌───────┴────────────────────────────────▼────────────┐
        │ Runtime（确定性，事实来源）                           │
        │ 任务 DAG · 依赖 · 谱系与尝试次数 · 事件                │
        │ run 任务：计划检查 → 干跑 → 完整运行 → 证据检查      │
        │ agent 任务（setup / debug / diagnose）：交给回调执行   │
        │ 收尾闸门：只有 runtime 能结束一次运行                  │
        └───────────────────────┬──────────────────────────────┘
                                │ C：由 Planner 在自己的对话里执行
                                │ D：交给上下文独立的 worker（诊断最多 3 个并行）
```

## 4. 机制

| # | 机制 | 做法 | 针对的问题 |
|---|---|---|---|
| 1 | 三阶段验证 | ① 加任务时检查计划：命令不能过滤或重定向输出，必须有 smoke 命令，正则只有一个捕获组，工作目录存在，每个 claim 只有一个计数的变体；② 干跑：smoke 命令必须正常退出、打印训练过程和指标行，通过了才放行完整运行；③ 证据检查：完整运行的日志里必须同时有训练过程和指标 | 6 次证据类失败 |
| 2 | 结束权归 runtime | 收尾提议只在每个 claim 都有足够的计数值，或有附带尝试记录的"无法测量"理由时才被接受 | 没验证完就宣布完成 |
| 3 | 进度字段由 runtime 计算 | 有没有进展、是否在原地打转（同一错误签名重复）由 runtime 算；下一步做什么由 Planner 决定 | 让 LLM 只做需要判断的事 |
| 4 | 停滞与重新规划 | 停滞 3 次就重新规划，有进展的一轮减 1；重新规划时清空 Planner 的对话，用账本和任务列表重新开始；超过 3 次就按现状打分 | 反复做无效修复 |
| 5 | 假设是一等公民 | task ledger 记录每个推断出来的设置和依据，并随结果一起写进 metrics 的备注 | Deep SVDD 的训练计划冲突 |
| 6 | 协议冲突时两种都跑 | 每个 claim 只有一个变体计数，其余作为诊断 | Deep SVDD |
| 7 | 派活模板 | 目标、工具和资料、边界、上下文引用、完成标准、工作量上限 | 交接时信息丢失 |
| 8 | 失败替换与重连 | 用 replace 替换失败的任务，等着它的任务自动改为等新任务；每条谱系最多 8 次 | 无效的反复调试 |
| 9 | 完整留痕 | trace 记录模型看到的每条消息，可以用 `replay_messages` 重建任意一次请求；工具调用经过前置守卫和后置钩子 | 无法事后还原模型看到了什么 |
| 10 | 断点续跑 | 每个图节点存 SQLite checkpoint，包括 runtime 状态和 Planner 的对话 | 长运行中途崩溃 |

## 5. 实验设计

| 组别 | 文件夹 | 要回答的问题 |
|---|---|---|
| A | `SingleAgent` | 基线：ReAct harness |
| B | `Multiagent/FixedPipeline` | 代码路由的固定流水线（v3.1） |
| C | `Multiagent/PlannerRuntime` | 主要的新架构 |
| C⁻ | `Multiagent/PlannerRuntimeNoGates` | C 去掉闸门：闸门贡献了多少 |
| D | `Multiagent/PlannerWorkers` | C 加 worker：上下文隔离有没有额外价值 |

- 评估逐层报告：跑通了吗 → 证据合规吗 → 在容差内吗；每次失败打 MAST 类别标签，另加"基础设施"一类；主分数不用 LLM 裁判。
- 事先写下的预测：C 和 D 主要减少证据类失败，成功率可能提升但幅度有限；D 不一定比 C 好；真正的数值差距（如 Deep SVDD）架构帮不上忙。
- 测试集：用户新建的论文数据集（v3 的 5 篇已成为开发集）；每组 30 次只能分辨大的差别。
