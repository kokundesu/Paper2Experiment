# v4 设计依据：6 篇论文的精读笔记

整理于 2026-10-16。HiRAS 是我读的全文和附录里的 prompt；其余 4 份是子 agent 读原文（arXiv HTML 或 PDF 全文）后的笔记，我汇总、翻译并核对过。标"未核实"的内容，原文里查不到或者只出现在图里，没有确切数字。

每篇按同样的结构写：做了什么、关键数据、对本项目的启示。最后一节列出每条设计决定对应哪篇论文。

## 1. HiRAS（2026，专门做论文复现）

**出处**：Hong et al., *HiRAS: A Hierarchical Multi-Agent Framework for Paper-to-Code Generation and Execution*, arXiv 2604.17745v2（2026-04）。

### 1.1 它要解决的问题

已有的复现系统（PaperCoder、AutoReproduce）基本都是**固定的顺序流水线**，每个阶段用写死的 prompt 调用，"全局监督有限"：没有任何组件看着整个运行，没人检查中间产物、诊断失败、回头重新调用前面的阶段，所以早期的错误会一路传下去，导致流程卡住或仓库不完整（§1）。已有的分层系统（FMH、AutoGen）里的 manager 多半只是"传话"，HiRAS 要做的是**主动监督的 manager**。

### 1.2 结构

| 层级 | 角色 | 产出 |
|---|---|---|
| 第 1 层 | global manager，管 plan / analysis / code / exec 四个 agent | 整体协调 |
| 第 2 层 | planning manager，管 4 个规划子 agent | `plan.md`、`architecture.md`、`dependency.md`、`config.yaml` |
| 执行层 | analysis agent、coding agent、execution agent | 分析文件、代码、`results/*.log` |

- 所有 agent 都是 ReAct agent，共享一个文件系统工作区；所有 agent 都有 `list_dir`、`read_file`、`write_file`，只有执行 agent 还有 `bash`（§3.1–3.3）。
- 每个 agent 最多 K 轮"推理 + 行动"，可以提前调用 `end_task`；**论文没有给出 K 的值**，也没有给 manager 的时间、token 或重试预算。
- Algorithm 1（§3.3）：一个 agent 的每一轮要么调工具，要么递归调用一个下属（带子指令），要么 `end_task(report)`；K 用完就把最后的推理当报告返回。

### 1.3 manager 的规则（附录 Fig. 11、12、19 的 prompt）

- **global manager**：一次只调用一个 agent，不能在循环里批量调用 coding agent；每一步都要确认文件存在、内容完整，才往下走；`components.txt` 里每个组件都要有分析、都要被实现，日志里不能有错误；下属报告上游产出有问题，就先检查那份产出，再让负责的 agent 重做；**检查完所有日志、确认没有错误之前，不许调用 `end_task`**；它对最终结果负责。
- **planning manager**：自己不写文件，只派活；要求下属完整读完文件（不许截断）；4 份计划文件都齐全、详细，才能结束；失败时要尽可能多地把上下文交回 global manager。
- **execution agent**：只能用 bash 运行；遇到错误要判断是代码的问题还是计划的问题，然后**报告给 global manager，"修问题不是你的职责"**；严禁记录没有实际跑出来的结果；每个实验写一份日志。

### 1.4 结果和消融

| 设置 | Code-Dev（o3 裁判）Qwen3 / DeepSeek | 完整 PaperBench（4o-mini 裁判）Qwen3 / DeepSeek |
|---|---|---|
| PaperCoder | 36.9 / 40.8 | 11.5 / 16.9 |
| AutoReproduce | 31.7 / 41.5 | 11.2 / 17.1 |
| 专门化 agent | 37.5 / 47.5 | 15.1 / 18.7 |
| + agent 内部迭代改进 | 40.5 / 51.2 | 18.2 / 19.5 |
| + 分层 manager（HiRAS） | **45.7 / 57.4** | **19.1 / 21.5** |

- 加 manager 这一步：Code-Dev 上 **+5.2 / +6.2** 个百分点；但要求真正跑通的完整 PaperBench 上只有 **+0.9 / +2.0**。
- Claude-Sonnet 在 Code-Dev 上 64.1%。
- **没有报告**：token 或时间成本（Limitations 只说"可能更高"）、manager 干预了多少次、抓到了什么。
- 作者自认的主要瓶颈是**执行**：文件之间的依赖、import 错误、环境搭建、下载模型和数据（§6.2）。附录 C 的例子：一个仓库 Code-Dev 69.7%，完整 PaperBench 只有 11.3%。

### 1.5 对本项目的启示

1. "上层检查 + 带指令重做"有效，但在"能不能真正跑通"这一环帮助很小，而这正是我们的主要难点。
2. HiRAS 的检查全靠 LLM 读文件；**能用代码判断的，我们交给 runtime 判断**（日志有没有训练过程、指标有没有打印）。
3. "执行者只报告、不自己修"，和我们"执行器确定性、调试交给单独的任务"一致。
4. "确认没有错误才能结束"，对应我们的收尾闸门。

## 2. MAST：Why Do Multi-Agent LLM Systems Fail?

**出处**：Cemri, Pan, Yang et al., arXiv 2503.13657v3（NeurIPS 2025）。

### 2.1 方法

- 7 个开源多智能体框架（MetaGPT、ChatDev、HyperAgent、AppWorld、AG2/MathChat、Magentic-One、OpenManus），共 1642 条标注轨迹；这些系统的失败率在 41% 到 86.7% 之间。
- 分类体系来自 150 多条轨迹（平均每条超过 1.5 万行），6 位专家用扎根理论编码；3 轮校准后标注者一致性 κ = 0.88，在新领域上 κ = 0.79。
- LLM 自动标注（o1，few-shot）：准确率 0.94，F1 0.80，κ 0.77；平均每条轨迹 $1.8。

### 2.2 分类：3 大类、14 种失败模式

| 大类 | 占比 | 失败模式（占比） |
|---|---|---|
| **系统设计问题** | 44.2% | 违反任务要求 11.8；违反角色分工 1.5；**重复已完成的步骤 15.7**；对话历史丢失 2.8；**不知道何时结束 12.4** |
| **agent 之间不一致** | 32.3% | 无故重置对话 2.2；该问不问 6.8；偏离任务 7.4；**隐瞒其他 agent 需要的信息 0.85**；忽视其他 agent 的输入 1.9；**推理和行动不一致 13.2** |
| **验证不足** | 23.5% | 过早结束 6.2；**没有或不完整的验证 8.2；错误的验证 9.1** |

（占比的分母论文没写清楚，看起来是"所有被标注的失败实例"的份额，这是笔记作者的推断。）

### 2.3 干预实验（附录 H）

| 系统 | 基线 | 改 prompt | 改拓扑 |
|---|---|---|---|
| AG2，GPT-4 | 84.75 | 89.75 | 85.50（不显著，p = 0.4） |
| AG2，GPT-4o | 84.25 | 89.00 | 88.83（p = 0.03） |
| ChatDev，ProgramDev | 25.0 | 34.4 | **40.6** |
| ChatDev，HumanEval | 89.6 | 90.3 | 91.5 |

- 拓扑干预：AG2 加一个**只有它能结束对话**的 Verifier（prompt 里明确写"假设的值不算数"）；ChatDev 把 DAG 改成环，CTO 确认所有审查都通过才结束。
- 作者结论：**改拓扑比改 prompt 有效**，但即使最好的修复"也不算大幅提升"。论文内部对 +9.4 和 +15.6 来自哪种改动有 3 种互相矛盾的说法，引用时要小心。

### 2.4 关于验证的结论

- 只在最后一步做低层检查（能编译、没有 TODO）是不够的，即使 prompt 要求了彻底验证；ChatDev 的国际象棋例子通过了审查，却仍有运行时错误。
- 要在**多个阶段**验证，在生成过程中持续收集测试输出，同时检查低层正确性和高层目标。
- 验证类失败在成功的运行里也会出现，所以"验证通过"本身也要被审计。

### 2.5 我们的失败对应到 MAST

| 我们的失败 | MAST 类别 |
|---|---|
| Planner 漏掉 `--verbose`，日志里没有训练过程 | 违反任务要求，加上验证不完整（只在最后才发现） |
| agent 用 grep 过滤输出，证据丢失 | 隐瞒其他环节需要的信息；本质是"agent 站在了证据的路径上" |
| 能量指标在训练之外单独算 | 违反任务要求（用更容易的替代品代替要求的测量） |
| 工作目录不存在导致崩溃 | 不属于 MAST，算基础设施问题 |
| Deep SVDD 的系统性差距 | 可能根本不是多智能体的失败；如果是，属于"该问不问"（未声明的超参数被直接假设） |

## 3. Towards a Science of Scaling Agent Systems（Google，2025）

**出处**：Kim et al., arXiv 2512.08296v3（2026-04 修订）。

### 3.1 设置

- 5 种架构：单 agent（SAS）、独立（只汇总、不交叉检查）、中心化（1 个 orchestrator + 3 个子 agent）、去中心化（全互联辩论）、混合。论文明确说**不研究 agent 专门化**这个维度。
- 6 个基准（BrowseComp-Plus、Finance-Agent、PlanCraft、WorkBench、SWE-bench Verified 子集、Terminal-Bench 子集），9 个模型（GPT-5 系列、Gemini 2.x、Claude Sonnet 3.7 到 4.5），共 260 种配置。

### 3.2 主要结果

| 基准（任务特点） | 单 agent | 多 agent 相对变化 |
|---|---|---|
| Finance（可拆分、可并行） | 0.349 | +57% 到 **+80.8%**（中心化最好） |
| **PlanCraft（严格顺序）** | 0.568 | **−39.1% 到 −70.0%** |
| SWE-bench（7 个工具） | 0.522 | −2.1% 到 −14.9% |
| Terminal-Bench（2 个工具） | 0.344 | 中心化 −19.2% |

六个基准合计，多 agent 的平均变化是 −0.3%（标准差 37.5%）。机制：在 PlanCraft 上，中心化系统把本来只有 3 步的任务拆成人为的子任务，协调消息吃掉了 token 预算。**决定协调是否有用的是顺序依赖，而不是任务复杂度。**

| 架构 | 成功率 | 轮数 | 错误放大（轨迹层面） | 每千 token 的成功 |
|---|---|---|---|---|
| 单 agent | 0.466 | 7.2 | 1.0 | 67.7 |
| 独立 | 0.370 | 11.4 | **17.2** | 42.4 |
| 中心化 | 0.463 | 27.7 | **4.4** | 21.5 |
| 混合 | 0.452 | 44.3 | 5.1 | 13.6 |

- 轮数随 agent 数超线性增长；超过 3 到 4 个 agent，每个 agent 分到的推理就太薄了。
- 在控制效率之后，错误放大本身不是显著的预测因子。

### 3.3 必须更正的一点

"单 agent 成功率超过约 45% 后，加 agent 收益为负"这个阈值，来自一个交互项（β = −0.236），在**聚类稳健标准误下不再显著**（p = 0.105）。稳健的是主效应："单 agent 基线越高，多 agent 收益越小"。另外，论文**没有研究固定角色流水线**（也就是我们的 B）。所以不能说它"解释了"我们 single ≈ multi 的结果，只能说方向一致。

### 3.4 对本项目的启示

1. 强顺序的关键路径上只保留一个推理中心（Planner）。
2. worker 只用于真正独立的子任务（比如各个 claim 的诊断），最多 3 个左右，彼此不直接通信。
3. worker 的产出必须经过中心检查才能改变状态（独立汇总的错误放大是 17.2 倍）。
4. 执行留在确定性的 runtime，不作为 LLM 工具。
5. 对 Haiku 这类模型的迁移性未知：论文里没有 Haiku 级别的模型。

## 4. Magentic-One（Microsoft，2024）与 Anthropic 的多智能体研究系统（2025）

### 4.1 Magentic-One

**出处**：Fourney et al., arXiv 2411.04468。**注意：论文没有附 orchestrator 的 prompt**，账本字段、阈值和重置规则来自 AutoGen 开源代码（`microsoft/autogen`，`_magentic_one` 目录），代码可能和论文实验时的版本不同。

| 机制 | 内容 |
|---|---|
| task ledger | 已确认的事实、待查事实（以及去哪查）、待推导事实、有根据的猜测，加一份计划；只在开始和重新规划时改写 |
| progress ledger | 每轮回答 5 个问题：请求完成了吗、在原地打转吗、有进展吗、下一个谁说话、给它什么指令；代码里每个字段都是 `{reason, answer}`，JSON 解析失败最多重试 10 次 |
| 停滞计数 | 论文说阈值"≤ 2"；代码里 `max_stalls = 3`，**有进展的一轮计数减 1**（所以是"净停滞"，不是"连续停滞"） |
| 重新规划 | 反思哪里出了错，更新事实和计划；**清空所有 agent 的上下文**，用新账本重新开始 |

- 消融：用普通的 GroupChat 代替 orchestrator（去掉账本、计划、进度跟踪），性能**下降 31%**（相对值，绝对数只在图里）。
- 错误分析中第二常见的是"**验证不足**"：没验证完就宣布完成。

### 4.2 Anthropic 的研究系统

**出处**：Anthropic Engineering, *How we built our multi-agent research system*（2025-06-13）。

- 结构：lead agent 制定计划并存进外部记忆；并行派出 3 到 5 个子 agent，每个用独立的上下文搜索，再交回压缩过的结果；最后由 citation agent 加引用。
- **派活必须说清楚**：目标、输出格式、可用的工具和资料来源、清晰的任务边界；否则子 agent 会重复劳动或留下空白。
- 子 agent 把结果写成文件，只交回轻量的引用，避免"传话游戏"。
- 在内部评测上，Opus 4 带 Sonnet 4 子 agent 比单个 Opus 4 好 90.2%；但 token 用量约是普通对话的 15 倍；token 用量单独就能解释 80% 的性能差异。
- 作者自己指出，多智能体**不适合**：所有 agent 需要同一份上下文的任务、依赖多的任务，以及大多数编程任务。
- 生产经验：出错后从断点恢复，而不是从头再来；全量 tracing；"告诉 agent 某个工具在失败，让它自己调整"效果出奇地好。

### 4.3 对本项目的启示

1. 采用两本账，但能算的布尔字段（有没有进展、是否打转）交给 runtime 计算，LLM 只决定下一步做什么、怎么交代。这是超出两份来源的设计选择，要作为我们自己的决定来说明。
2. 停滞阈值 3，有进展的一轮减 1；重新规划时清空 worker 上下文，保留账本和产物。
3. 派活消息用固定模板，worker 交回结构化报告和文件引用。
4. 每次唤醒都带上标准化的错误签名和重复次数。

## 5. AutoReproduce 与 PaperBench

### 5.1 AutoReproduce

**出处**：Zhao et al., arXiv 2505.20662v4（ACL 2026；数字以 v4 为准，v2 的摘要数字已被替换）。

- 从论文出发写代码（不用官方仓库），每次复现一个指定的实验；两个 agent（研究 agent、代码 agent），三个阶段（文献综述、"论文谱系"、代码开发）。
- **干跑**：先用少量数据批次推断张量形状；完整训练脚本先用 `break` 提前退出做一次干跑，检查训练循环的逻辑。
- 先诊断再修改；每个子阶段最多调试 20 次，通常 5 到 8 次就能修好，再多很少有用。
- 消融（Claude-3.5-Sonnet）：去掉调试和修正，**LLM 打的对齐分只降 1.65，性能差距却从 31.62 涨到 88.78**。也就是说，LLM 裁判看不出代码能不能跑通。
- 主要错误是模型内部的张量形状错误；人工评审还发现论文经常不写学习率调度。

### 5.2 PaperBench

**出处**：Starace et al., arXiv 2504.01848v3（OpenAI）。

- 20 篇 ICML 2024 论文，从零复现，禁止用作者代码；评分用作者参与制定的评分树，共 8316 个叶子，分"写代码 / 能运行 / 结果对上"三类，由 LLM 裁判逐叶打分（o3-mini 裁判 F1 0.83；在"写代码"类叶子上只有 0.72）。
- **agent 最常见的问题是提前收工**。IterativeAgent 去掉了提交工具，强制干到时间用完，o1 从 13.2 升到 24.4；**但同样的改动让 Claude-3.5-Sonnet 从 21.0 降到 16.1**，因为 Claude 本来就不提前停。
- 按叶子类型看：写代码得分较高，能运行和结果对上接近零（例如 o1：43.3 / 4.5 / 0.0）。
- "结果对上"类叶子只认复现运行开始之后新生成的文件，事先写死的结果不算。
- 人类博士 48 小时达到 41.4%；o1 在 1 小时后就停滞了。

### 5.3 对本项目的启示

1. 我们从官方仓库出发，绕开了 PaperBench 里最容易的部分，难点集中在它们几乎拿不到分的"能运行"和"结果对上"。
2. 坚持不用 LLM 当裁判（AutoReproduce 的消融是最直接的证据）。
3. 加干跑闸门；Debugger 先诊断再修改，有次数上限。
4. 结束权交给 runtime；防提前收工的机制要**按模型配置**，因为同一机制对 o1 和 Claude 的效果相反。
5. 证据只认本次运行生成的日志。

## 6. 设计决定与依据对照

| 设计决定（实现位置） | 依据 |
|---|---|
| 唯一的 Planner，交声明式的任务 DAG（`ExperimentPatch`） | Cuti / dsh；Google（顺序任务保持单一推理中心） |
| runtime 是事实来源，状态可序列化、可断点续跑（`p2e.runtime.Runtime.state`） | Cuti；Anthropic（从断点恢复） |
| 三阶段验证：计划检查、干跑、证据检查 | MAST（多阶段验证）；AutoReproduce（干跑）；PaperBench（只认本次运行的输出） |
| 结束权归 runtime（`check_finish`） | MAST（只有验证者能结束）；HiRAS（确认无错才结束）；Magentic-One（验证不足） |
| 进度字段由 runtime 计算，停滞 3 次重新规划、有进展减 1 | Magentic-One（AutoGen 代码） |
| 重新规划时清空对话，保留账本和任务列表 | Magentic-One |
| task ledger 里的"假设"一节 | Magentic-One 的事实四分法；MAST 的"该问不问" |
| 一个 claim 只有一个计数的变体，其余作为诊断 | 协议冲突时两种都跑（Deep SVDD 的教训） |
| 派活模板；worker 交回结构化报告 | Anthropic；Magentic-One |
| 每条谱系最多 8 次尝试 | AutoReproduce 附录 A.2 |
| 诊断最多 3 个并行，worker 之间不通信 | Google；Anthropic |
| 模型可见即已记录；工具流水线钩子 | dsh / Cuti |
| C⁻ 组用来衡量闸门的贡献 | MAST 和 AutoReproduce 都指向验证是主要收益来源 |
| 不用 LLM 裁判 | AutoReproduce 消融；PaperBench 裁判在代码类叶子上 F1 只有 0.72 |
